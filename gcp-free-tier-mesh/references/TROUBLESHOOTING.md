# Troubleshooting (`gcp-free-tier-mesh`)

実戦構築（5 GCP プロジェクト × `e2-micro` × 13 コンテナ展開）で発生した全例外と解決策の記録です。

| Symptom | Root Cause | Fix |
|:---|:---|:---|
| `Error 403: USER_PROJECT_DENIED` (`Caller does not have required permission to use project ...`) | Single ADC or Service Account only has permissions on one project, lacking `serviceusage.services.use` / IAM on other Google-account-owned projects. | Use `scripts/apply_tf_tokens.py` to inject per-account `gcloud auth print-access-token` tokens into `TF_VAR_access_tokens`, or invite a shared SA to all projects. |
| `Error 400: UREQ_PROJECT_BILLING_NOT_FOUND` when enabling `compute.googleapis.com` | Target GCP project is not linked to any active Billing Account. | Run `scripts/link_billing.py --pair <email>:<project>` to detect and link each account's open Billing Account. |
| `gcloud billing accounts list` returns `Listed 0 items` | Project owner's Google account has no Billing Account of its own. | Pass `--fallback-owner <email> --fallback-billing-id <id>` to `scripts/link_billing.py`; it grants `roles/billing.projectManager` to the billing owner and links cross-account. |
| `Error 400: There is a peering operation in progress on the local or peer network` | Hub-side and spoke-side `google_compute_network_peering` resources targeting the same hub VPC ran concurrently. | Chain **all** hub-side and spoke-side peering resources sequentially with `depends_on` (see `templates/terraform/main.tf`). |
| Cross-VPC Peering traffic blocked despite `source_tags` Firewall rule | GCP network tags (`source_tags`) do not propagate across VPC Network Peering boundaries. | Use explicit peered subnet CIDRs in `source_ranges` (`allow-internal`, `allow-redis-from-peered-vpcs`). |
| `deploy_compose.py` times out even when containers are `(healthy)` | Substring check `"exit" in output.lower()` on `docker compose ps --format json` matched the JSON key `"ExitCode"`. | Match exact JSON status tokens (`'"unhealthy"'`, `'"exited"'`, `'"dead"'`) in `vm-docker-deploy/scripts/deploy_compose.py`. |
| `chown: invalid user: 'ppbb:ppbb'` on GCE VM | `enable-oslogin = "TRUE"` creates OS Login users (e.g. `btczoa_gmail_com`) instead of local user `ppbb`. | Run `id ppbb \|\| sudo useradd -m -s /bin/bash ppbb` before configuring `/home/ppbb/.ssh/authorized_keys` on the Redis hub VM. |
| `Error: unable to open database file` / `SqliteError: 14` on mounted `./data` | Non-root container user (`USER deno`, UID 1000) cannot write to host-mounted `./data/<service>` owned by OS Login user. | Run `chmod 777 ~/app/<stack>/data/<service>` on each new data subdir (`scripts/deploy_mesh.py` handles this). Avoid `chmod -R` on existing Deno KV SQLite files (`Operation not permitted`). |
| `e2-micro` OOM / HDD swap thrashing or `coin-trade-bot` missing `HY_SECRET_KEY` / `SLACK_BOT_TOKEN` | Running > 3 Deno containers on 1 GB RAM causes HDD swap thrashing; master `conf/.env` had empty secret placeholders. | Cap each VM to `<= 3` containers + `DENO_V8_FLAGS=--max-old-space-size=96` + 1 GB Swap; use `scripts/sync_env_secret.py` to copy non-empty keys from verified `.env` sources. |
| `Uncaught SyntaxError: ... does not provide an export named 'getSignalType'` (`btc-dca-bot`) | Shared `constants.ts` refactor omitted `getSignalType` export in `btc_dca_bot`. | Restore `export function getSignalType(...)` in `src/btc_dca_bot/shared/constants.ts`, rebuild image, and re-export via `scripts/package_images.py`. |
