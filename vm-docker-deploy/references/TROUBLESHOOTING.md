# Troubleshooting (`vm-docker-deploy`)

| Symptom | Root Cause | Fix |
|:---|:---|:---|
| `bash: docker: command not found` | The VM was newly provisioned and Docker Engine has not been installed yet. | `deploy_compose.py` will auto-detect and run apt-get provisioning. Alternatively, run the installation script manually. |
| `cp: omitting directory '/ssh-key/id_key'` | Host-side mount target (`~/.ssh/google_compute_engine`) did not exist when Docker started, causing Docker daemon to auto-create a directory instead of a file. | Run `mkdir -p ~/.ssh && touch ~/.ssh/google_compute_engine` before container launch, sync the actual key, and run `docker compose down && docker compose up -d`. |
| `scp: dest open ".ssh/...": No such file` | The remote user home directory does not yet contain a `.ssh` directory. | Run `mkdir -p ~/.ssh && chmod 700 ~/.ssh` via `gcloud compute ssh` before attempting `scp`. |
| `container is unhealthy` | Health check command failed or depends_on timeout expired (e.g., SSH tunnel target unreachable). | Inspect logs using `sudo docker compose logs <service>`. Verify tunnel host/port and remote authentication. |
| `Permission denied (publickey)` in tunnel | SSH key permissions on VM are too permissive or user is incorrect. | Ensure remote key permissions are strictly `chmod 600 ~/.ssh/google_compute_engine`. |
| `Error 403: USER_PROJECT_DENIED` during multi-project Terraform apply | The active ADC or Service Account only has permissions on one project (e.g. `nanbingjun-project`) and lacks `serviceusage.services.use` / IAM roles on other Google-account-owned projects. | Invite a shared deployment Service Account to all target projects (`roles/editor` + `roles/serviceusage.serviceUsageAdmin`), or configure per-project SA key JSON paths via `provider "google"` aliases (`credentials_files`). |
| Cross-VPC Peering traffic blocked despite `source_tags` Firewall rule | GCP network tags (`source_tags`) do not propagate across VPC Network Peering boundaries. | Replace `source_tags` with explicit peered subnet CIDRs in `source_ranges` on both hub and spoke firewall rules (e.g., port `6379` for Redis). |
| `There is a peering operation in progress` during hub-and-spoke VPC Peering | Creating multiple `google_compute_network_peering` resources concurrently (even from spoke projects targeting the same hub VPC) triggers a GCP API race condition on the peer network. | Chain ALL hub-side and spoke-side `google_compute_network_peering` resources sequentially using `depends_on`. |
| OOM / HDD swap thrashing on `e2-micro` (1 GB RAM) | Running too many Deno containers or frequent `deno eval` healthchecks exceeds the ~650-750 MB usable RAM, causing heavy swapping on `pd-standard` HDD. | Cap each `e2-micro` to `<= 3` containers (e.g., `redis-tunnel` + 2 Bots), add 1 GB Swap as safety margin, and offload WebUIs to ad-hoc Cloud Run. |
| `Error 400: UREQ_PROJECT_BILLING_NOT_FOUND` when enabling APIs | Newly created GCP projects are not yet linked to an active Billing Account, blocking `compute.googleapis.com` activation. | Run `gcloud billing accounts list --account=<email>` to get an open Billing Account ID, then link it via `gcloud billing projects link <project-id> --billing-account=<id> --account=<email>` before re-running Terraform. |
| Account has 0 Billing Accounts (`Listed 0 items`) when linking a project | The project owner's Google account has no Billing Account of its own, so another account's Billing Account must be linked across accounts. | Grant `roles/billing.projectManager` on the target project to the Billing Account owner (`gcloud projects add-iam-policy-binding <project> --member="user:<billing-owner>" --role="roles/billing.projectManager"`), then run `gcloud billing projects link` as `<billing-owner>`. |
| `deploy_compose.py` times out even when containers are `(healthy)` | Substring check `"exit" in output.lower()` on `docker compose ps --format json` falsely matches the JSON key `"ExitCode"`. | Match exact JSON status tokens (`'"unhealthy"'`, `'"exited"'`, `'"dead"'`) instead of bare `"exit"`. |
| `Error: unable to open database file` / `SqliteError: 14` on mounted `./data` | Non-root container user (e.g. `USER deno`, UID 1000) cannot write to host-mounted `./data` created by OS Login user. | Run `chmod -R 777 ~/app/<stack>/data` (or `chown -R 1000:1000`) on the VM before starting containers. |
